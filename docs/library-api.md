# Local library API and lifecycle

Status: implemented for the single development owner on localhost. This is not a multi-user or public API. Start the five Compose services before using the examples below. All examples use synthetic files generated by the command in `README.md`.

## Upload and processing

```powershell
curl.exe -sS -F "file=@media/fixtures/sample.pdf" http://127.0.0.1:8000/documents
curl.exe -sS http://127.0.0.1:8000/documents
```

The upload response includes `id` (document), `version_id`, `job_id`, `filename`, and an initial `status`. Each version moves through `queued`, `processing`, `ready`, or `failed`; failures retain `error_message`. Poll `GET /documents/{id}` for versions and `GET /jobs/{job_id}` for job state and attempt count. `POST /jobs/{job_id}/retry` retries a failed job or re-enqueues a job that has remained queued for over one minute. A replacement file is uploaded with `POST /documents/{id}/versions` using the same `file` form field. Old versions remain available and the new version becomes current.

For a failed extraction, a retry can succeed if the failure was transient. Retrying an image-only PDF without OCR will fail again. Admission failures return HTTP 422 with a reason and do not create a version. The API reads no more than 10 MiB plus one byte from its spooled upload before validation. The multipart parser can spool the incoming request before this limit is checked; this endpoint is for local development only. PDF admission also caps page count at 100; DOCX ZIP entries are capped at 2,048 and 32 MiB total expanded size. Original files are stored in a private Compose volume under opaque keys, separate from the web container. The Next.js route at `/api/library/...` proxies browser requests to FastAPI.

## Library and sources

| Operation | Route |
| --- | --- |
| List and filter | `GET /documents?folder={uuid}&tag={uuid}&favorite=true&q={text}` |
| Document and version history | `GET /documents/{id}` |
| Rename, assign folder and tags, set favorite | `PATCH /documents/{id}` with `title`, `folder_id`, `tag_ids`, or `favorite` |
| Create or list folders | `POST /folders` with `{"name":"..."}`; `GET /folders` |
| Create or list tags | `POST /tags` with `{"name":"..."}`; `GET /tags` |
| Inspect ordered passages | `GET /documents/{id}/versions/{version_id}/passages` |
| Open a version's original | `GET /documents/{id}/versions/{version_id}/original` |

The first extraction recipe is `blocks-v1`. A passage ID depends on the version ID, recipe, ordinal, and text hash, so reprocessing the same version with this recipe retains IDs. PDF locators contain a 1-based page and offsets in extracted page text. TXT and Markdown contain character ranges in decoded UTF-8 text. DOCX locators identify a body block and, for table cells, row and column. The UI links PDF passages to the original page and displays extracted text as a fallback; text formats display the extracted passage and character or block location. No pixel-accurate PDF highlight is claimed.

## Deletion and limits

`DELETE /documents/{id}` returns a cleanup `job_id` with HTTP 202. It tombstones the document in the database transaction, so list, detail, passage, and original-file routes stop serving it immediately. The background cleanup job removes original files and passage rows, clears blob references and organization links, then reports `ready` or `failed` at `GET /jobs/{job_id}`. A failed cleanup can be retried through the job retry route. The tombstone, versions, and job record remain as an operations trail; this is not physical erasure of database backups. `docker compose down --volumes` destroys local Compose volumes and all local FaroDocs data.

The current parser limits and synthetic corpus are documented in [extraction-spike.md](extraction-spike.md). Search, chat, OCR, identity, permissions, and external providers are separate later stages. Do not use private documents or real credentials in this local preview.
